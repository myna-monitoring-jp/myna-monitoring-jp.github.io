# Claude Code 一気通貫改修プロンプト

あなたは現在、`myna-monitoring-jp.github.io` のGitHub Pagesサイトを構築しているリポジトリのルートで作業しています。

このサイトを、毎日公開される「マイナ保険証・マイナンバー関連モニタリング」の正本として、企画・調査・データ更新・HTML生成・品質確認・公開まで一気通貫で動く状態に改修してください。

**計画だけ提示して止まらず、現行コードの監査、実装、テスト、データ移行、GitHub Pages向けビルド設定、可能な範囲でのコミット・プッシュ・公開確認まで実行してください。**  
不明点は合理的な初期値を設定し、設定ファイルで変更できるようにしてください。重大な判断が必要な場合だけ、最後に「要確認事項」として残してください。

## 1. 今回の最終目標

固定URLで公開されるサイトに、毎日次の情報が反映されるようにしてください。

1. 直近24時間を中心とするトップニュース
2. 前日からの差分
3. ネガティブなニュース
4. ポジティブなニュース
5. マイナ保険証・オンライン資格確認・マイナポータル・マイナアプリ等の不具合
6. 自治体・保険者の資格情報、負担割合、資格確認書等の不具合
7. 医療機関・医療ベンダー・健保・周辺ITの障害、個人情報事故、サイバー攻撃、生成AIへの誤投入
8. 政府・行政の広報、広告、動画、SNS、タイアップの炎上・批判・反応・効果
9. 全国代表性のある世論調査
10. X、Yahoo!コメント、App Store等で目立つ非代表サンプルの反応
11. 今日の優先ウォッチ
12. 出典元への押下可能なリンク
13. 日別アーカイブ
14. Teamsに貼れる朝の要約

サイトの見た目は、既存モックの紫系ダッシュボードとカード型UIを基本にしつつ、現在の実装を全面破壊せず、情報精度と運用性を優先して改善してください。

## 2. 重要な実装方針

### 2.1 既存実装の監査

最初に次を確認し、`docs/CURRENT_STATE_AUDIT.md` に記録してください。

- 使用フレームワーク、ビルド方式
- GitHub Pagesの公開方式
- データの保存場所
- 現在の検索・取得ロジック
- 毎日更新が動いているか
- HTMLやカードがハードコードされている箇所
- リンクが押せない原因
- 重複記事や誤った日付が出る原因
- 一次情報より転載記事が優先される原因
- SNS反応を世論と誤認する可能性
- 自動生成内容のレビュー有無
- GitHub Actionsの失敗箇所
- 秘密情報がフロントエンドに露出していないか

監査後、`docs/IMPLEMENTATION_PLAN.md` を作り、そのまま実装を続けてください。

### 2.2 破壊的変更の回避

- 現行データを削除しない
- 変更前にバックアップを作る
- 既存URLが可能な限り壊れないようにする
- 既存のアーカイブを新スキーマへ移行する
- 大規模な技術スタック変更は、現行構成で要件達成できない場合に限る
- 現行リポジトリが静的HTML中心なら、まず静的MVPとして完成させる

### 3.1 discover：発見検索

`query_catalog.yml` を読み込み、少なくとも次の5パスで検索します。

1. 広域ニュース発見
2. 政府・自治体・関係機関の公式情報探索
3. 発見した事象の深掘り
4. SNS・コメント・アプリレビュー等の反応確認
5. 前日案件の復旧・訂正・拡大・沈静化確認

時間窓を使い分けてください。

- 直近24時間：朝レポートの中心
- 72時間：検索インデックス遅延の補完
- 7日：継続案件・炎上推移
- 30日：背景、既存批判、類似事例

検索日時、検索語、検索プロバイダー、取得件数、エラーをログに残してください。

検索APIの秘密情報が必要な場合は、次のように抽象化してください。

- 既存の検索プロバイダーがあれば優先利用
- `SEARCH_PROVIDER` で切替
- APIキーはGitHub Actions Secretsまたは環境変数
- キーがなくても、公式RSS・サイトマップ・公開フィード・手動投入JSONで最低限動く
- フロントエンドへAPIキーを埋め込まない
- 利用規約やrobots.txtを無視する実装をしない

### 3.2 fetch：本文取得

- 検索スニペットだけで確定記事を作らない
- 一次情報、記事本文、公開PDF等を取得する
- 取得日時、HTTPステータス、最終URL、ページタイトル、公開日時を保存
- PDFはテキスト抽出し、必要ならページ番号を保持
- 取得失敗時は検索スニペットから断定せず `fetch_failed` とする
- 同一URLの再取得をキャッシュする
- レート制限・再試行・タイムアウトを実装する

### 3.3 extract：構造化抽出

各候補から以下を抽出してください。

- タイトル
- 発生日
- 公表日
- 更新日
- 対象地域・対象者
- 制度・システム名
- 何が起きたか
- 何が新しいか
- 影響人数・件数・期間
- 原因
- 回避策
- 復旧日時
- 公式対応
- 出典
- SNS反応
- ファクトチェック対象の主張

日付は混同せず分けて保存してください。

```text
occurredAt
publishedAt
updatedAt
detectedAt
lastMaterialUpdateAt
```

LLMを使う場合は、必ずJSON Schemaに適合する構造化出力にしてください。  
`ANTHROPIC_API_KEY` 等が存在する場合だけAPIを使い、存在しない場合も決定論的な抽出で最低限動くようにしてください。

### 3.4 cluster：重複除去・同一事象統合

以下を同一事象へ統合してください。

- Yahoo!ニュースと元記事
- 通信社配信と系列転載
- 同じプレスリリースの転載
- 同じ自治体発表を引用する複数記事
- 同一障害の初報・続報・復旧報
- 同じ広報物に対する複数反応

重複判定には次を組み合わせてください。

- canonical URL
- タイトル類似度
- 本文類似度
- 主体
- 発生日
- システム名
- 影響地域
- 固有表現
- 公式発表URL

「媒体数」は、同一通信社・同一系列・同一記事転載を水増ししないでください。

### 3.5 verify：一次情報確認

情報源優先順位は `source_registry.yml` に従ってください。

原則：

```text
一次情報
> 政府・自治体・関係機関の公式発表
> 信頼できる主要報道
> 専門媒体
> SNS・コメント
```

事実の確定には一次情報を優先し、以下を実装してください。

- 影響人数は原則公式値
- 報道しかない場合は「報道によると」
- SNSしかない場合は事象を確定しない
- 公式と報道で数字が異なる場合は差異を表示
- 「未公表」「未確認」を明示
- 推測で数字を埋めない
- 古い公式ページの更新日時を最新情報と誤認しない

### 3.6 reaction：国民・現場の声

全国代表性のある世論調査と、非代表サンプルを別データ型・別UIにしてください。

#### 代表性のある調査

保存項目：

- 調査主体
- 実施期間
- 標本数
- 抽出方法
- 回答方法
- 設問文
- 選択肢
- 比率
- 誤差・限界

#### X、Yahoo!コメント、App Store等

保存項目：

- 投稿・レビュー日時
- 主張の要約
- 肯定／懸念／不満／誤解／期待
- 返信、RP、いいね、引用、表示回数、コメント数
- 取得日時
- URL
- 代表投稿か
- `representativeOfPopulation: false`

数値を取得できない場合は推測しないでください。

実在しない反応を「国民の声」として生成しないでください。  
予測は必ず `communicationRisk` として別管理してください。

### 3.7 diff：前日差分

前日データと比較し、次を自動判定してください。

- NEW
- 拡大
- 縮小
- 公式対応
- 訂正
- 復旧
- 計画停止開始
- 計画停止終了
- 反応増加
- 記事化
- 沈静化
- 大きな動きなし

「公式終了発表がない」だけを理由に障害継続と断定しないでください。  
予定終了時刻を過ぎた場合は、「予定時刻経過」「延長告知未確認」と表現してください。

### 3.8 score：影響度と話題度の分離

別々のスコアを持たせてください。

#### 社会的影響度

- 医療・行政手続への直接影響
- 対象人数
- 全国／地域範囲
- 個人情報・セキュリティ
- 継続時間
- 代替手段
- 患者・住民負担

#### 話題・炎上規模

- 独立媒体数
- 全国紙・テレビ・Yahoo!ニュース等への波及
- SNS反応量
- 著名人・議員・団体への波及
- 公式の謝罪・削除・中止
- 二次転載
- 反応増加速度

「社会的影響が大きいが話題は小さい事案」と「話題は大きいが実害は限定的な事案」を区別してください。

## 5. 広報・炎上判定を実装する

広報案件は次の3分類にしてください。

```text
reported_backlash
active_watch
active_stable
```

`active_stable` はさらに分けます。

```text
quiet
positive
```

### 5.1 広報案件で記録する項目

1. 起点の公式投稿・広告・動画・タイアップ
2. 訴求意図
3. 現に確認できた批判
4. 主な論点3〜5点
5. 事実誤認と正当な指摘の切り分け
6. 公式の補足・訂正・削除・謝罪・中止
7. 二次転載・報道化
8. 炎上要因
9. 反応数
10. 取得日時
11. 既存批判か、新しい広報起点か

### 5.2 炎上認定

単に反対投稿が存在するだけでは炎上としないでください。  
次の複数条件を満たす場合に `reported_backlash` とします。

- 批判投稿の量が大きい
- 複数の二次転載
- 全国紙・テレビ・Yahoo!ニュース等で記事化
- 著名人・議員・業界団体へ波及
- 公式側が謝罪・訂正・削除・中止・回収
- 24時間で反応が急増

### 5.3 既存批判と新規広報の分離

公金受取口座のような案件では、必ず次を別々に判定してください。

```text
existingCriticism
newCampaignTriggeredReaction
communicationRisk
```

過去に大きく拡散した投稿があっても、新しい広告を見て発生した反応でなければ、新規広告の炎上件数へ入れないでください。

## 6. 状態と7日ルール

使用する状態：

```text
new
attention
follow_up
resolved
scheduled_maintenance
quiet
archived
needs_review
```

日本語表示：

```text
新着
要注視
続報待ち
解消済
計画停止
沈静化
アーカイブ
要レビュー
```

曖昧な「WATCH」「継続」は使用しないでください。

### 6.1 ダッシュボード非表示

- 基準は `lastMaterialUpdateAt`
- 7日間重要更新がなければダッシュボードから非表示
- 詳細・検索・アーカイブには保持
- `pinned=true` は表示継続
- 日数は `config/app.yml` で変更可能
- 重要更新とは、公式発表、独立した追加報道、反応急増、影響規模変更、復旧、原因確定、謝罪、削除、中止

## 7. 日次HTMLとサイトUI

### 7.1 日別レポート

毎日、次のファイルを生成してください。

```text
public/reports/myna_news_YYYY-MM-DD.html
```

構成：

1. ヘッダー
2. 今朝の総括
3. 前日からの差分
4. ネガティブなニュース
5. ポジティブなニュース
6. 広報・SNS炎上／批判動向
7. 世論・反応の傾向
8. 今日の優先ウォッチ
9. 主な情報源

### 7.2 各ニュースカード

必ず同じカード内に配置します。

```text
A. ニュース自体
B. 国民の声・現場の声
C. 事実関係・補足
D. 出典・リンク
```

反応がない場合は、

```text
新規の有意な反応は確認できず
```

と表示してください。

### 7.3 ダッシュボード

固定URLのトップで次を表示してください。

- 最終更新日時
- 最終正常更新日時
- 今朝の総括
- 重要ニュース
- 新規全国障害の有無
- 不具合3カテゴリーの件数
- 広報3分類の件数
- 世論の主要論点
- 今日の優先ウォッチ
- 日別レポートへのリンク
- Teams投稿文コピー
- 共有URLコピー

### 7.4 リンクのクリック要件

ここは必ず実装・自動テストしてください。

- 実体のある `<a href="https://...">`
- 外部リンクは `target="_blank"`
- `rel="noopener noreferrer"`
- ボタン全体をクリック可能
- `pointer-events: auto`
- カード全体を覆う透明リンクは禁止
- 疑似要素やオーバーレイでリンクを塞がない
- ステータスバッジは押せる見た目にしない
- ボタン文言は「一次情報を開く」「報道記事を開く」「X投稿を開く」等
- `href=""`、`href="#"`、`javascript:void(0)`は禁止
- 日別HTML内のリンクも同様
- Playwrightまたは同等のE2Eテストを作る

### 7.5 デザイン

- Meiryo UI / Meiryo優先
- 紫系ダッシュボード
- 重要度、炎上度、事実判定をバッジ表示
- PC、タブレット、スマートフォン対応
- 印刷時にカードが分断されにくい
- 色だけに依存しない
- キーボード操作・フォーカス表示
- 読み込み失敗・空データ表示

## 8. データのレビューと公開品質

次は自動公開前に `needs_review` へ送ってください。

- 個人情報・セキュリティ事故
- 医療現場に直接影響する重大障害
- 炎上認定
- 対象人数が大きい案件
- SNSの代表投稿
- 公式と報道で数字が異なる案件
- 実名・ハンドル名を掲載する案件
- 取得不能箇所をLLMが補完しようとした案件

MVPで完全な人手承認画面が難しい場合は、次を作ってください。

```text
data/review_queue.json
public/review/index.html
```

未承認でも、一次情報で確定した事実部分だけは掲載可能とし、未確認の反応・評価は出さないでください。

## 9. GitHub Actions・毎日更新

現行のデプロイ方式を確認したうえで、以下を実装してください。

### 9.1 ワークフロー

- 毎朝の定時実行
- 手動実行 `workflow_dispatch`
- 失敗時に既存の公開サイトを壊さない
- データ更新
- QA
- ビルド
- GitHub Pages公開
- 生成データのアーカイブ
- 更新サマリのArtifact保存
- 失敗ログのArtifact保存

例：

```text
.github/workflows/daily-monitoring.yml
.github/workflows/deploy-pages.yml
```

既存ワークフローがある場合は統合し、二重デプロイを避けてください。

### 9.2 秘密情報

- APIキーはGitHub Actions Secrets
- 必要なSecretsを `docs/SECRETS_SETUP.md` に列挙
- キーがなくても公式RSS・手動投入でサイトビルドは成功
- 秘密情報をログ・JSON・HTMLへ出力しない

### 9.3 Teams共有

MVP必須：

- 「共有URLをコピー」
- 「Teams投稿文をコピー」
- 毎朝の要約テンプレート自動生成

オプション：

- 組織で承認されたTeams Workflow/Webhookが設定済みなら自動投稿
- 未設定ならサイト公開は失敗させず、投稿用テキストをArtifactとして保存

## 15. 禁止事項

- 検索スニペットだけで事実確定
- 出典のないニュース生成
- SNSだけで事故を事実認定
- SNSを全国世論として表示
- 実在しない国民の声を生成
- 系列転載を独立媒体数として水増し
- 計画停止を障害として扱う
- 既存批判を新規広告の炎上として扱う
- 公式終了発表がないだけで障害継続と断定
- マイナアプリの不具合をオンライン資格確認全体へ拡張
- 未公表人数の推測
- 公開日と発生日の混同
- 低品質なまとめサイトを一次根拠にする
- フロントエンドへAPIキーを埋め込む
- 押せないリンク
- 空のリンク
- カード全体を覆う透明リンク
- テストせずに公開
- 現行アーカイブの削除
